# Coordinator duties and agent parity

**Status:** moved here from [AGENTS.md](../AGENTS.md#coordinator-and-agent-parity) on 11 Nov 2026 so role agents no longer load it on every invocation. Rule levels are unchanged. **Read when:** you are the coordinator (before coordinating a deliverable or invoking a role) or you edit a role config.


The **coordinator** is the chat session the user talks to (Claude Code or Codex). It does the following:

- selects deliverables, style profile and tier;
- invokes role agents for the assigned scope (Claude Code: the `Agent` tool with `subagent_type` set to the role name; Codex: the custom agent of that name);
- passes matching revisions;
- publishes the [user storyboard review page](mark-storyboard-workflow.md#user-storyboard-review-page) whenever Film returns a `ready-for-dev` scene-sheet revision or Film adds look frames, built with `scripts/storyboard-page/build.py` from Film's `review-rows.json`, and relays the verdicts back;
- follows the [agent invocation defaults](#agent-invocation): whole stage per call (shot groups for painting and rendering), inline mechanical edits, separate checking.

<a id="coordinator-duties"></a>
**Coordinator duties kept in other documents** (user, 7 Nov 2026). Each rule lives in the linked document; read that section when its moment comes:

- **Start and pick:** create `delivery.md` and `task.md` ([delivery record](delivery-workflow.md#delivery-record-and-handoff-checks), [task file](delivery-workflow.md#task-file)); have the user pick a concept ([ideation](delivery-workflow.md#ideation)); propose the open deliverable closest to W8 first ([finish first](#wip-limit)).
- **Before the user sees pictures:** run the [viewer check](sequence-workflow.md#viewer-check); voice takes for choosing are at most 10 s ([audition cap](delivery-workflow.md#voice-audition-cap)).
- **Review page:** batch ready shots into one [review round](#review-rounds) (no daily cap); record the page URL in `delivery.md` in the same turn; read verdicts, render the next [stage](render-rules.md#render-stage) and pin passed finals with `pin.mjs` ([moving a shot on](sequence-workflow.md#painted-shot-by-shot), W7).
- **Publish and post:** after a delivery render or a cover pick or fix, run `store.py publish` and give the user `publish/<channel>/<PROJECT>/<ID>/` (W8.2); when the user says it is posted, `store.py publish <ID> --posted <date>` (W8.3) ([publish folder](../README.md#publish-folder)).
- **Fix rounds:** one `fixlist.md` per round ([AI12](delivery-workflow.md#ai12)); after two fix passes on a shot group the user decides ([fix-pass cap](boss-asset-workflow.md#latest-production-rules)).
- **Rules and repo:** list `proposed` rule changes for the user at a stage end and apply them in a docs-only PR ([DP03–DP04](contributing.md#tools-and-document-improvements)); tooling waits for the [maintenance window](contributing.md#maintenance-window); check that a PR is unmerged before pushing to its branch ([merged-PR check](contributing.md#merged-pr-check)); a user note repeated on a second episode goes into [user taste](user-taste.md); tick W8.3 when the user says a video is posted.

[Role configs](../AGENTS.md#coordinator-and-agent-parity) install no runner; a role agent never invokes the next role.

`.claude/agents/<role>.md` and `.codex/agents/<role>.toml` must carry the same name, description and instructions. `tests/agents.test.ts` enforces this, so edit both in the same change. Claude front matter also carries a required `tools:` allowlist (Claude-only) that keeps each role's startup context small. Add a tool there before a role depends on it. Optional Claude-only `model:` and `effort:` lines pin a role's model and reasoning effort; the front matter is the current record and `git log -p .claude/agents/` its history. The coordinator may override them per call. OpenCode copies (`.opencode/agents/<role>.md`) are generated from the Claude files by `python3 -I scripts/opencode-agents.py`; rerun it after editing a role (the same test checks them). OpenCode reads skills from `.claude/skills` and `.agents/skills` directly and MCP servers from `opencode.json`. ZCode copies (`.zcode/agents/<role>.md`, GLM-5.3) are generated the same way by `python3 -I scripts/zcode-agents.py`; ZCode reads skills from `.agents/skills` and MCP servers from `.agents/mcp.json`, a symlink to `.mcp.json`.

<a id="resolve-the-selection"></a>
## Resolve the selection before writing

Moved from [delivery-workflow](delivery-workflow.md#resolve-the-selection-before-writing) on 11 Nov 2026.


1. Read the user's request and the existing episode delivery record. Reuse an explicit selection; do not ask again when the user already chose the formats or supplied a scoped revision request.
2. For a new video, run the [ideation round](delivery-workflow.md#ideation) first; the chosen concept settles the genre, medium and tone it names. If the selection or a [style profile](delivery-workflow.md#style-profile) field the concept leaves open is missing or materially ambiguous, ask with the harness's structured-question tool: `AskUserQuestion` in Claude Code, `request_user_input_async` in Codex; if neither exists, ask in chat. Ask only for what the prompt leaves open, in one call in the user's language: the **selection** with three choices, **both**, **Short only**, **Long only**, showing the duration targets from production requirements (Thai example: “หัวข้อนี้ต้องการทำทั้ง Shorts และ YouTube แบบยาว หรือเลือกแบบใดแบบหนึ่ง?”), the **style** (genre/medium, voice, music) and the **target length** when none is stated or implied, and whether the user has a **look reference** (image, link or earlier episode) when the medium is illustrated or 3D. For an animated or illustrated deliverable, the same call also asks the [visual engine](delivery-workflow.md#visual-engine) unless the prompt or record names one. Do not ask about a choice the prompt or the delivery record already settles. A sent question, preselected option or elapsed wait is not an answer. Continue independent research while waiting; begin format-dependent writing/scene sheets only after the selection is resolved.
3. Record the answer or existing instruction in `scripts/<episode>/delivery.md`: selection, style profile and pipeline (`Full`), evidence of the user's choice, deliverable IDs, target durations and scope. `short`, `long` and `both` are authoring labels, not runtime fields. Default counts are one standalone Short and one Long when both are selected. A chapter series, multiple Shorts or additional edits require explicit scope; selecting both does not make every Long chapter a Short.
4. Create `scripts/<episode>/task.md` ([task file](delivery-workflow.md#task-file)) and route each selected deliverable through the [pipeline](delivery-workflow.md#pipeline-tiers): Ideation → Boat research → Preaw script → Boat fact-check → Film brief and written scene sheets → Boss shared assets/capabilities → Editor integration/editing. Shared research may feed both. A scriptwriting-only assignment ends with editorial handoff; selection does not authorize automatic downstream production, agent execution or cross-chat messaging.

Selection is complete when the record identifies the selected deliverables and the instruction resolving the choice. An explicit custom duration/scope overrides defaults with its reason recorded. For a new version of existing production, preserve existing IDs and evidence; record a migration map before changing paths or IDs. Workflow updates alone do not migrate historical episodes.

<a id="wip-limit"></a>
## Finish first


**Default (user, 3 Nov 2026):** any number of deliverables may stay open; none is parked. When the coordinator proposes what to work on next, or the user asks, it proposes the open deliverable closest to W8 first, and its next-step questions name that one. A deliverable waiting on the user is listed with the one decision it waits on. Evidence: on 3 Nov 2026 eight deliverables were open at once while six had been posted.

<a id="agent-invocation"></a>
## Agent invocation (coordinator rules)

**Default** for how the [coordinator](coordinator.md#coordinator-and-agent-parity) runs a tier's stages. Every role agent starts cold and rereads AGENTS.md and its core documents, so invocations cost context. A brief may override a rule with a recorded reason.

The rules that bind a role agent inside its own run (AI09, AI10, AI11, AI13) stay in [delivery-workflow](delivery-workflow.md#agent-invocation).

- **AI01 — One invocation per stage and revision.** Send the whole stage scope in one brief (every beat, shot or asset it covers), not one call per shot or fix. Batch review notes for the same owner into one revision. **Exception for painting and rendering stages:** Boss and Editor plate work, and Film spikes that paint or render, go one invocation per shot group of 3–5 shots (or one asset family). The delivery record lists the remaining groups. Cost grows with turns × accumulated context, and whole-stage runs measured 150–170 turns at 500–580k peak context (ZCPAINT, 30 Oct 2026).
- **AI02 — Coordinator does mechanical edits inline.** Small edits with no judgment call do not need a role agent: a value, typo, link or `Stage / Next owner` update, applying a change the owning role already decided and recorded, a [single-value fact-check correction](editorial-workflow.md#inline-fact-fixes), or reading status. Name the owning role in the change (e.g. "coordinator for Film, SS-R2.5"). New or substantially revised scripts, fact-checks, briefs, scene sheets, assets and Blender/render work always go to the owning role.
- **AI03 — Keep authoring and checking separate.** The role that checks a piece of work never runs in the same invocation as the one that wrote it (Boat's fact-check of Preaw's script). Boss and Editor runtime work (Blender, renders, audio generation) runs in their own agent, so logs and frames stay out of the coordinator's context.
- **AI04 — Fresh invocation per pass.** Each pass of a role (a new revision, a review-and-fix round, the next shot group) starts a fresh invocation with a short brief: inputs by path and revision, the decisions made since the last pass and the delta to do. Do not resume one agent across passes: its context and cost grow with every pass (BLOOP-EP01-SHORT, 30 Oct 2026: Boss ran 7 passes in one context, 466 calls, 40 % of the session's tokens). Continue an agent (Claude Code: `SendMessage`) for a clarification of the pass it just finished, or for a follow-up fix on the same shots when that pass ended under about 60 calls and less than an hour ago (its files are still in its warm cache, so a fresh invocation would only pay to reread them).
- **AI05 — Point, don't paste.** Briefs name file paths, revisions and stable IDs. They do not paste document or handoff content into the brief, and they list only the trigger documents the stage needs beyond the role's core reads.
- **AI06 — Wait once for long jobs.** Batch renders and Blender jobs into one run and wait for it once (a background job or `Monitor`), not with repeated polling. Prove the shot with sampled frames or a low-resolution pass before a full render. A run longer than about 10 minutes renders in per-shot chunks, so a stop resumes at the next chunk, and writes progress (chunks or frames done of total, elapsed, estimate) to its log under `out/logs/`; the coordinator answers status questions from that log's last lines. [AI10](delivery-workflow.md#ai10) covers who waits.
- **AI07 — Short sessions, handoff through the record.** A coordinator session covers one stage, or one review-and-fix round, for one deliverable. Before the session ends, the delivery record's `Stage / Next owner` cell, the [task file](delivery-workflow.md#task-file) and the handoff files carry everything the next step needs (revisions, open items, evidence paths). The next session starts from `task.md`, `delivery.md` and the named revisions, not from chat history. Start a new session rather than continuing one whose context is already long. Keep the model fixed within a session, because switching models restarts the prompt cache.
- **AI08 — One correction, one pass.** When a user correction touches several handoff files (a prop state, a hand side, a mirrored camera), the coordinator invokes once the role whose judgment the correction needs. That invocation updates every affected file (brief, scene sheets, index) with a change-log line naming each file's owner; the other owners review it in their next scheduled pass instead of a relay of invocations. Boss or Editor re-runs once, after the files agree.
- <a id="ai12"></a>**AI12 — One fix list, one pass per owner.** User verdicts and critic findings for a review round go into `scripts/<episode>/fixlist.md` (one line each: shot, note, owner, status). The coordinator sends one invocation per owner when the user has finished that round on the page, not one per note as notes arrive; the user can ask for a single note to go now. Evidence: ZCONDO2 Draft (4 Nov 2026) ran nine single-note Boss and Editor passes in three hours (hands, grip, face height, caption shade).

Independent deliverables (a Short and a Long) may run as parallel invocations. Stages that depend on each other stay in tier order.

<a id="review-page"></a>
## Storyboard review page (coordinator)

Moved from [mark-storyboard-workflow](mark-storyboard-workflow.md#user-storyboard-review-page) on 11 Nov 2026. That section keeps what Film writes (`review-rows.json`, the first pass, the row content) and the "not a gate" rule; these are the coordinator's parts.

- **Tabs:** three tabs over the same shot rows: **สตอรีบอร์ด** (storyboard), **Draft** and **Final**, each with its own pass/change verdict per shot. A status bar and the tab labels count the shots passed per tab (for example สตอรีบอร์ด 13/13 · Draft 5/13 · Final 0/13), live from the verdicts; each row shows three dots for its passed tabs and a 🔒 when `pinned`.
- **Clips:** the Draft and Final tabs each show one cut of the whole video (`node scripts/storyboard-page/clips.mjs <ID> <review-rows.json> --full [--draft]`; the draft at half size), recorded as `draftCut` / `finalCut` with each shot's `clips.draft` / `clips.final` (`src`, `in`, `out`, `cut`) pointing into it; "▶ ช็อตนี้ในคลิปเต็ม" plays the shot inside the cut and "▶ ดูทั้งคลิป" the whole cut ([render stage](render-rules.md#render-stage)). A single shot can also carry its own clip, a 360×640 proxy with about 1 s of each neighbour (`--shots=<ids> [--draft]`): "▶ ช็อตนี้" loops the shot's own frames and "▶ รอยต่อ" plays the whole clip. A shot without a clip for the tab reads `ยังไม่มี` and has no verdict buttons. The coordinator republishes the page when clips arrive or the revision changes.
- **Final cut:** the Final tab shows one clip of the whole video (`clips.mjs <ID> <review-rows.json> --full`, a 540×960 proxy in `finalCut`), and each row has a button that plays its shot inside that cut. A shot's final clip is keyed by its scene-cache keys, so a re-cut after a fix asks again only for the shots whose scenes changed ([W6](sequence-workflow.md#painted-shot-by-shot)).
- **Feedback:** each shot has a pass/change verdict and a free-text note per tab, stored in the artifact's `db` capability (`reviews/<shot ID>@<board|draft|final>`, fields `shot`, `stage`, `status`, `note`, `rev`, `hash`, `clip`, `updatedAt` and, after a re-answer, `prev`; open questions use `reviews/<Q ID>`) so the coordinator reads them back with `ArtifactData`. **Answers carry over (user, 1 Nov 2026):** `build.py` stamps each shot, question and clip with a content hash and a verdict holds while the hash of what it judged is unchanged, so republishing a revision keeps the user's answers on untouched shots. The storyboard hash covers the shot's text (title, VO, seen, sound, flag) and leaves out timing, so a retime after the voice lock keeps them; a Draft or Final verdict counts only for the clip file it was given on, so a re-rendered clip asks again. A changed item shows a `เปลี่ยน` badge with its old answer and asks again; Film may add a short Thai `changed` line on a shot to say what changed, and `previousVerdicts` is no longer needed. The coordinator reads a verdict as current when its `hash` matches the item's hash in the built page. A copy-all button covers viewers without `db`. User-owned open questions from the index appear as their own items.
- <a id="review-rounds"></a>**Review rounds — Requirement (user, 3 Nov 2026; daily cap removed by the user, 8 Nov 2026):** no limit on rounds per day. The coordinator republishes the page once per round, with every shot that is ready for a tab, not after each fix. The user marks only the shots to change; when the user says the round is done, the coordinator asks with the structured-question tool whether the unmarked shots on that tab pass, and on yes records them as `pass` with the note `default (round <date>)`. All change notes from one round go to each owner as one revision ([AI01](delivery-workflow.md#agent-invocation)). Evidence: `KSO-EP01-SHORT` reached storyboard page v7.
- **Recording — Requirement (user, 31 Oct 2026):** record the page URL in the same turn you publish it, in the deliverable's `delivery.md` (URL, scene-sheet revision, artifact version, and that verdicts live in its `db` under `reviews/<shot ID>@<stage>` with `rev`) and in the episode `handoff.md`, so a new or cleared session can find, read and republish the page without chat history. Republishing a later revision to the same URL updates both records. Also add the page URL and its scene-sheet revision to the index items table. The coordinator relays `change` notes to Film as a new revision request and records each verdict as user feedback with its date; a full set of storyboard `ok` verdicts is recorded as user approval of that revision only. A Final `ok` is the user's approval of that shot's picture for delivery: the coordinator pins it (`scripts/pin.mjs`) and records the pin in `delivery.md`.
