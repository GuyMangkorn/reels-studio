# Render rules

**Requirement** for every role that renders video or stills (Boss, Editor, Film, coordinator). Moved out of [AGENTS.md](../AGENTS.md#shared-agent-conventions) on 5 Nov 2026 so Preaw and Boat do not load them; the text is unchanged.

<a id="render-by-scene"></a>
- **Render by scene, keep the scenes (Requirement):** every video render goes through `scripts/render.mjs`, which renders one timeline scene at a time and keeps each in `$REELS_STORE/cache/segments/<CompositionId>/` ([scripts/segments.mjs](../scripts/segments.mjs)). The same segments serve review and delivery: a review clip (`--range`, `scripts/storyboard-page/clips.mjs`) renders the scenes it touches into the cache, the user's final approval pins those segments (`scripts/pin.mjs`), and the delivery render and every re-edit reuse each scene whose inputs did not change, so after an edit only the touched scenes are painted: a timeline edit (caption, cue, overlay) touches its scene; a code edit touches the scenes of that shot when the shot has its own [shot file](sequence-workflow.md#one-shot-one-file), and otherwise every scene of the episode; a shared kit, character or set edit touches every scene that uses it; a length change touches every scene. Before painting, the render logs one `repaint N of M:` line with the reason per scene (shared code or art, shot file, timeline/neighbour/options, video length, first render), and a pinned-scene stop names the same reason. A re-edit that would change a pinned scene (a caption, a cue, shared code) stops the render: `--repaint=<shot>` renders it again and returns it to the user's Final tab for a new approval, or `--keep-pinned` ships the approved picture unchanged, with the reason recorded. **Default:** for painted deliverables one shot is one timeline scene, so approval, pinning and re-edits each touch exactly one shot; a scene that must hold several shots (a continuous camera move, a dissolve chain) is recorded in the scene sheet and reviewed as one unit. Never replace this with a whole-timeline `npx remotion render` for a deliverable or a re-edit; a whole-timeline render is for a frame-range check with `--no-cache` only, recorded with the reason. Measured in [DF-20261031-render-speed](dev-findings/DF-20261031-render-speed.md); workflow in [shot-by-shot review](sequence-workflow.md#painted-shot-by-shot).
<a id="render-stage"></a>
- **Render stage before every video render (Requirement; user, 7 Nov 2026):** a deliverable's video renders run in three stages, in order, and the renderer names the stage before each render in one line of its reply: `Render stage: <draft cut | final cut | delivery | range check> · <shots or frames> · gate: <task.md line>`.
  1. **Draft cut**: the whole video once at half size (`scripts/storyboard-page/clips.mjs <ID> <review-rows.json> --full --draft`), once the storyboard and the [voice lock](delivery-workflow.md#voice-lock) have passed (W5). The Draft tab shows that one cut split into the storyboard shots, and the user marks the shots to change. After fixes the same command runs again and repaints only the touched scenes.
  2. **Final cut**: the whole video once at full size (`clips.mjs --full`), only when every shot's draft passed (task.md W5.3 at N/N; W6).
  3. **Delivery**: `render.mjs <CompositionId>` with no review flag, only when every scene is pinned (W7, `pin.mjs pin-rows`). A delivery render becomes final for the user only when `store.py publish` copies it into the [publish folder](../README.md#publish-folder) (W8.2).

  The draft paints at half size (`paintScale` 0.5, 540×960 for a 1080×1920 video) so it renders faster and is small to watch; it is cached under its own variant and never reused for delivery. A request that does not name a stage ("render", "ทำคลิป") means the next stage in task.md. Skipping a stage needs the user's choice: their words that say so ("ข้าม draft", "render final เลย"), or else one structured question giving the time of both options from the latest `out/logs/render-*.jsonl`. The scripts enforce stages 2 and 3: `clips.mjs --full` stops while a shot has no draft clip, and a delivery render stops while a scene is unpinned. `--skip-draft="<reason>"` and `--unreviewed="<reason>"` override them only after that choice, with the user's words and date as the reason. Evidence: the user, 7 Nov 2026, reported renders that skipped the draft and went straight to a full final, so every fix waited on a long render.
<a id="review-renders"></a>
- **Review renders reuse the scene cache (Requirement):** a video rendered for the user to look at goes through the scene cache. The final cut and range checks are full size, so a later delivery reuses them: the final cut with `scripts/storyboard-page/clips.mjs --full` for the [storyboard review page](mark-storyboard-workflow.md#user-storyboard-review-page), or a range with `scripts/render.mjs <CompositionId> --range=<from>-<to>` covering the frames under review plus about one second either side. The draft (`clips.mjs --full --draft`, `render.mjs --draft`) is half size and cached apart ([render stage](#render-stage)); it is also the quick look whenever the user asks for one. `--preview` is the old name of `--draft` (merged 7 Nov 2026). Stills for frame checks (`--stills`, `scripts/qa-sheet.sh`, caption-zone and lead-height measurements) stay full size.
<a id="stills-one-chrome"></a>
- **Stills on one Chrome (Requirement):** QA and review stills are rendered with `scripts/render.mjs <CompositionId> --stills --frames=<a,b,...>` or by piping `ID FRAME OUTPUT` lines into `node scripts/stills.mjs <bundleDir|entry.ts>` ([scripts/stills.mjs](../scripts/stills.mjs)), never with `npx remotion still` in a per-frame loop (each call bundles, starts Node and launches Chrome). A script calling `@remotion/renderer` opens one browser and passes it as `puppeteerInstance`; Remotion ignores `browserInstance` and launches a Chrome per call. Measured in [DF-20261031-render-speed](dev-findings/DF-20261031-render-speed.md#stills-and-browser-reuse-31-oct-2026-claudep5-brush-rendering-optimize-fd68e1).
