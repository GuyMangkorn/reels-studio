# Storyboard review page

Merged on 15 Nov 2026 from the Film section of `docs/mark-storyboard-workflow.md` and the coordinator section of `docs/coordinator.md`; the rules are unchanged. Film writes the rows; the coordinator builds, publishes and reads the page.

## Rows and page content (Film)


**Default:** after Film marks a scene-sheet revision `ready-for-dev`, the coordinator publishes the deliverable's review page so the user can check the plan before plates are rendered. **One page per deliverable** (user, 1 Nov 2026): the same artifact URL carries every scene-sheet revision, draft clip and final clip from the first storyboard pass to the last final; the artifact keeps earlier versions, and the `reviews.json` mirror in Git keeps the verdicts. For painted deliverables the page drives the [shot-by-shot review](../../../docs/sequence-workflow.md#painted-shot-by-shot).

- **First pass — Requirement (user, 31 Oct 2026):** the user sees a storyboard right after the script, before the [voice lock](../../../docs/delivery-workflow.md#voice-lock), to judge camera and VO only. Film's pre-lock staging pass also writes `review-rows.json` with `"untimed": true` and no `start`/`end`: per shot the full Thai VO and a `seen` cell that leads with the camera (shot size, angle, movement) and then what is seen; no times or lengths appear. Film reports `review page: pending`; the coordinator builds and publishes it the same way, at the URL that later timed revisions reuse. Film later adds the look frames to the same rows file (`looks`, `look` per beat; [W3](../../../docs/sequence-workflow.md#painted-shot-by-shot)) and the coordinator republishes. In a legacy Light deliverable, Film writes these rows from the brief's shot list. The first pass is not a gate: the voice lock and later stages continue while it is open, and its `change` notes enter the next scene-sheet revision.

- **Form:** a private HTML review page written for the user in Thai. Agent-facing sheets stay in English and own the shot direction.
- **Build — Requirement (31 Oct 2026):** the layout is fixed in `scripts/storyboard-page/template.html` (taken from the WORLD FOG SS-R2 page). With each `ready-for-dev` revision Film writes the rows in Thai as `review-rows.json` beside the index (schema and example: `scripts/storyboard-page/example.json`) and reports `review page: pending`. The coordinator runs `python3 -I scripts/storyboard-page/build.py <review-rows.json>`, which writes `out/review-pages/<deliverable>/index.html` with its `pv/` files, and publishes it as a Claude Artifact (below) to the same URL for each later revision of that deliverable. **Artifact again (user, 19 Nov 2026):** the plain HTML page served by `serve.py` (17–19 Nov 2026) is now only the fallback for a harness without the artifact tools. A layout change goes into the template, never into one page; a hand-written page does not count as the review page.
- **Content:** one table, one row per shot, with beat-name group rows. Columns: shot ID with Thai start time and length · short Thai title with the full Thai VO · what is seen (one or two plain sentences, camera folded in) with any brief deviation or open item flagged, and the sound in a few words · the tab's clip (Draft tab only) · review. The Final tab has no table (below). The storyboard tab is text only. Keep cells short enough to scan; the scene sheet keeps the detail. The page carries no painted storyboard art per shot. Each beat header shows the **look frame** of its location (Film, [W2](../../../docs/sequence-workflow.md#painted-shot-by-shot)): `looks` at the top level of `review-rows.json` and `look` on each beat; beats at the same location share one look frame. A shot without a capture may show a plain SVG schematic (frame, horizon, figure boxes, caption band) drawn from the scene sheet, labelled as a schematic.
- **Not a gate:** the page adds no approval gate to `ready-for-dev` unless the delivery record asks for one. Under the [fast lane](../../../docs/delivery-workflow.md#fast-lane) the delivery record asks for one: the storyboard tab's verdicts are the R2 lock (script, storyboard, look frames, voice), and Boss builds after it passes. Boss and Editor may start blockout while review is open; changes from review follow the normal revision rules. **Default:** Boss paints finished-grade plates for a shot only after its Draft verdict is `ok`, and the coordinator sends fixes as one batched revision of 3–5 shots, so a look note costs one fix pass instead of one per shot.

## Publishing and reading the page (coordinator)

- **Publish (Claude Code):** publish the built folder with the artifact tools (`publish_files` on the claude-artifacts server, or `Artifact` where that tool exists): `index.html` plus every `pv/` file `build.py` prints, then on the first publish declare `capabilities: {"db": {}}`. Republish to the same slug with the live `base_version` for every revision, clip arrival or round. The page saves each click to the db (`reviews/<key>`) and updates live across tabs and devices; opened without a db, the copy-all button is the fallback.
- **Fallback serve (Codex, OpenCode, or no artifact tools):** `python3 -I scripts/storyboard-page/serve.py <review-rows.json> [--port N] [--lan]` serves the built page at `http://127.0.0.1:8765/` (default port; one port per deliverable when several are open) and saves every click to `reviews.json` beside `review-rows.json`. Run it as a background job and give the user the URL; `--lan` prints a phone URL on the same Wi-Fi. The page polls every 2 s, so answers from another tab, agent edits to `reviews.json` and a rebuilt page appear without a manual reload (a rebuilt page reloads itself once nothing is being typed). Opened without the server, the page says so and the copy-all button is the fallback.
- **Read (every harness):** for an artifact page, first read the db's `reviews` collection (`db_list`, limit 1000) and save the returned docs to a file, then run `python3 -I scripts/storyboard-page/verdicts.py <review-rows.json> --pull <file>`, which copies them into the `reviews.json` mirror; for a served page, run it without `--pull`. It prints per tab the passed, changed and open shots and every answer marked `current` (its hash matches the current rows), `stale` (the item changed after the answer) or `orphan`; `--json` gives the same as data. Commit `reviews.json` with the revision it judged.
- **Tabs:** three tabs: **สตอรีบอร์ด** (storyboard) and **Draft** over the same shot rows, each with its own pass/change verdict per shot, and **Final** with one verdict for the whole video. A status bar and the tab labels count the shots passed per tab and show the Final state (for example สตอรีบอร์ด 13/13 · Draft 5/13 · Final รอดู), live from the verdicts; each row shows two dots for its passed tabs and a 🔒 when `pinned`.
- **Accept all (user, 17 Nov 2026):** on the storyboard and Draft tabs, the "ผ่านทั้งหมด (N)" button (renamed 21 Nov 2026) marks every shot of that tab that has no answer yet as `ok` on a second click within 5 s (no `confirm()` dialog: the artifact frame can block it, which left the button dead); shots marked `change` keep their answer. It is the user's own end-of-round pass, so the coordinator's [round question](#review-rounds) is needed only when shots are still open when the user says the round is done.
- **Clips:** the Draft tab shows one half-size cut of the whole video (`node scripts/storyboard-page/clips.mjs <ID> <review-rows.json> --full --draft`), recorded as `draftCut` with each shot's `clips.draft` (`src`, `in`, `out`, `cut`) pointing into it; "▶ ช็อตนี้ในคลิปเต็ม" plays the shot inside the cut and "▶ ดูทั้งคลิป" the whole cut ([render stage](../../../docs/render-rules.md#render-stage)). A single shot can also carry its own clip, a 360×640 proxy with about 1 s of each neighbour (`--shots=<ids> [--draft]`): "▶ ช็อตนี้" loops the shot's own frames and "▶ รอยต่อ" plays the whole clip. A shot without a clip for the tab reads `ยังไม่มี` and has no verdict buttons. The coordinator republishes the page when clips arrive or the revision changes.
- **Final (user, 17 Nov 2026):** the Final tab shows the delivery render itself, the file that will be published, as one player: `render.mjs <ID> --rows=<review-rows.json>` writes it to the rows as `finalCut` once every draft passed ([render stage](../render/SKILL.md#render-stage)). There is no per-shot verdict: the user marks the whole video `ok` or `change` with one note that gives times for any fix (key `video@final`, hashed on the file, so a re-render asks again). The coordinator maps a `change` note to shots by time and routes the fixes; per-shot fixes belong to the Draft tab ([W6](../../../docs/sequence-workflow.md#painted-shot-by-shot)). Rows from before this change may still carry `clips.final`; the page ignores it.
- **Feedback:** each shot has a pass/change verdict and a free-text note on the storyboard and Draft tabs, and the video has one on the Final tab, stored in the artifact's `db` as `reviews/<key>` (mirrored into `reviews.json` beside `review-rows.json` by `verdicts.py --pull`; a `serve.py` page writes `reviews.json` directly) (key `<shot ID>@<board|draft>` or `video@final`, fields `shot`, `stage`, `status`, `note`, `rev`, `hash`, `clip`, `updatedAt` and, after a re-answer, `prev`; open questions use `<Q ID>`) so any harness reads them back with `verdicts.py`. **Answers carry over (user, 1 Nov 2026):** `build.py` stamps each shot, question and clip with a content hash and a verdict holds while the hash of what it judged is unchanged, so republishing a revision keeps the user's answers on untouched shots. The storyboard hash covers the shot's text (title, VO, seen, sound, flag) and leaves out timing, so a retime after the voice lock keeps them; a Draft or Final verdict counts only for the clip or file it was given on, so a re-rendered clip asks again. A changed item shows a `เปลี่ยน` badge with its old answer and asks again; Film may add a short Thai `changed` line on a shot to say what changed, and `previousVerdicts` is no longer needed. The coordinator reads a verdict as current when its `hash` matches the item's hash in the built page (`verdicts.py` checks this). A copy-all button covers a page opened without a store. User-owned open questions from the index appear as their own items.
- <a id="review-rounds"></a>**Review rounds — Requirement (user, 3 Nov 2026; daily cap removed by the user, 8 Nov 2026):** no limit on rounds per day. The coordinator republishes the page once per round, with every shot that is ready for a tab, not after each fix. The user marks only the shots to change; when the user says the round is done, the coordinator asks with the structured-question tool whether the unmarked shots on that tab pass, and on yes records them with `verdicts.py <review-rows.json> --pass-open <tab> --round <date>` (status `ok`, note `default (round <date>)`); for an artifact page add `--pull <file>` and send the `db_write ops` it prints (50 per call) so the page shows them too. All change notes from one round go to each owner as one revision ([AI01](../../../docs/delivery-workflow.md#agent-invocation)). Evidence: `KSO-EP01-SHORT` reached storyboard page v7.
- **Recording — Requirement (user, 31 Oct 2026):** record the page in the same turn you publish it, in the deliverable's `delivery.md` (artifact URL, scene-sheet revision, artifact version, and that verdicts live in its `db` under `reviews/<shot ID>@<stage>` with `rev`, mirrored to `reviews.json`; for a fallback page, the `serve.py` command and port) and in the episode `handoff.md`, so a new or cleared session can find, read and republish the page without chat history. Republishing a later revision updates both records. Also add the page URL and its scene-sheet revision to the index items table. Pages served with `serve.py` between 17 and 19 Nov 2026 keep their verdicts in `reviews.json`; when such a deliverable moves to an artifact, write its still-current answers into the new artifact's db once (`db_write`, `reviews/<key>`). The coordinator relays `change` notes to Film as a new revision request and records each verdict as user feedback with its date; a full set of storyboard `ok` verdicts is recorded as user approval of that revision only. A Final `ok` is the user's approval of the video for delivery: the coordinator pins every scene (`scripts/pin.mjs <ID> pin-rows <review-rows.json>`), publishes that same file (`store.py publish`) and records both in `delivery.md`.
